# Agent 运行台：主 Agent、子 Agent 与回复全过程

状态：原设计方案；0.21.0 已接入实际运行链路，交付范围、验证结果和未实现项见 [实施与验收](AGENT_WORKBENCH_021.md)。以下保留设计依据，不把所有设想标记为已验收。核对日期：2026-09-21。

目标：打开界面即可知道“正在为哪个岗位做什么、谁在处理、产出了什么、准备怎么回复、下一步是什么、是否需要我介入”。

## 1. 代码评审：已有能力与实际缺口

本方案依据当前源码，不能把源码状态直接视为已安装客户端能力。

| 已有能力 | 代码位置 | 缺口 |
| --- | --- | --- |
| 求职协调：规则安排、AI 排序、行动派发与执行记录 | `atlas-coordinator.ts`、`CoordinatorPanel.vue` | 行动分别关联 taskId、contactId、discoveryId，没有统一的全过程视图 |
| 持久化任务、取消、心跳、版本校验 | `atlas-task-queue.ts`、`atlas-task-records.ts` | 主要保留最新 step；没有完整父子关系和逐步事件历史 |
| 11 类 Agent 的提示词、启停、版本及实际模型调用记录 | `common/agents.ts`、`atlas-agents.ts`、`CareerAgents.vue` | 看到哪个角色调用了模型，但难以追溯到一个岗位或一段会话的整条流程 |
| 模型网关、串行调用、工具调用、用量和缓存 | `atlas-deepseek.ts`、`atlas-model-transport.ts` | 工具记录主要是名称；缺少分步骤的输入摘要、来源、开始和结束状态 |
| 搜索→详情→分析→联系→核验的汇总展示 | `CareerTasks.vue` | 搜索部分展示当前轮次，联系部分展示任务库存；两者不能作为单条任务进度条 |
| 话术生成、事实审校、程序校验、发送与回读 | `atlas-greeting.ts`、`atlas-assistant.ts`、`career-auto-reply.ts`、联系执行模块 | 草稿、检查、发送凭据分散；用户无法一眼判断是否真的发出 |

角色已存在不等于它正在运行。协调 Agent 完成安排后，应显示“安排已完成，子任务执行中”，不能一直显示“主 Agent 思考中”。手动触发的回复也不能强行挂在并未派发它的主 Agent 下。

### 本轮不扩大执行权限

沿用现有模型选择、额度、自动发送授权及重要事项确认规则。本次增加可见性和控制能力，不新建另一套调度器，不改变发送上限，不自动恢复当前暂停状态。用户偏好和个人资料从现有设置读取，面向开源不写死个人姓名、城市、薪资或 GitHub 地址。

## 2. 界面归属

不增加一级导航。保留“任务中心”和“Agent 管理”，明确职责。

| 入口 | 要回答的问题 | 调整 |
| --- | --- | --- |
| 全景总览／今日求职安排 | 现在在做什么？我先处理什么？ | 增加紧凑运行摘要：实际处理对象、当前步骤、待处理项、进入运行台 |
| 任务中心／Agent 运行台 | 谁在做？做到哪？卡在哪里？ | 作为默认页签；保留发送控制、同步覆盖和历史记录 |
| 沟通中心／当前会话 | 准备怎么回这位招聘者？ | 在消息编辑区旁显示当前回复任务、草稿、依据和检查结果 |
| 机会发现／当前岗位 | 为什么联系或放弃？招呼发出去了吗？ | 在岗位卡和详情增加同一任务的状态入口 |
| Agent 管理 | 此角色用什么提示词、模型和权限？ | 继续管理配置；增加“正在处理的任务”和从运行详情定位实际版本 |

全局顶栏只保留一个状态入口，例如“正在审校 · 某企业 / AI 产品负责人”。没有执行时显示“空闲／已暂停”，不显示虚构的待命动画。

## 3. 运行台布局

### 第一层：运行概览

显示当前账号、只建议／自动安排模式、暂停状态以及当前任务。任务数量和实际模型请求数量分开统计，例如“3 条流程未结束；1 次模型调用进行中，2 条等待”。

保留两个不同按钮：

- **暂停发送**：阻止新的发送动作，采集与分析按原授权继续。
- **暂停自动任务**：停止派发自动步骤，按现有执行器的中止规则处理在途任务。

任何取消都不能撤回已发出的平台消息。若点击暂停时发送已在途，显示“已请求暂停，当前发送正在核验”，不能直接显示发送已取消。

### 第二层：按工作对象组织

桌面宽屏使用“工作列表／步骤与协作／结果与介入”三栏；1280 宽度可合并后两栏为两栏布局，窄屏用列表进入详情。

**工作列表**：默认列出正在执行、等待本人处理的岗位或会话，其他历史折叠。每项显示企业、岗位、对象类型、当前步骤、最近更新时间。支持账号、任务类型、状态及日期筛选。默认按需关注排序，避免全部历史占据首页。

**步骤与协作**：主 Agent 及实际子任务以缩进任务树呈现，点击步骤查看对应结果。仅展示当前流程；不在首页铺开全部 Agent 的复杂网络图。

**结果与介入**：默认显示可读的结果；分为“结果”“依据”“运行记录”三个页签。原始技术字段放入高级详情，不默认展开 JSON。

### 节点统一展示

每个节点只显示：名称、执行者、状态、一句当前动作、耗时。详细输入、输出、工具、版本在点击后展示。

- **主 Agent**：求职协调，选择与排序已有能力，显示安排摘要和派发原因。
- **子 Agent**：实际执行的岗位分析、企业研判、招呼生成、话术审校、回复等。
- **系统步骤**：读取、去重、资格检查、队列、额度和发送核验，用“程序”标识。
- **本人处理**：经历确认、重要事项确认、结果不确定核实，用“待你处理”标识。

Agent 是角色，任务是这次工作的实例。一个角色处理多个岗位时分别显示实例；缓存命中显示“复用分析”，不算作新模型调用。一个结果被多个任务引用时显示“复用自…”，不复制执行次数。独立发起的任务显示“由你发起／定时触发／收到新消息”，保留真实来源。

## 4. 两条主要流程

### A. 岗位自动联系

1. 协调安排或机会发现创建任务，标明来源和授权。
2. 程序读取及去重，显示新增、更新、重复的实际数量。
3. 岗位分析 Agent 输出硬条件、经历依据、缺口和建议；不匹配在此结束，列明放弃原因。
4. 招呼 Agent 使用完整 JD、已确认经历和最新分析生成草稿。
5. 话术审校 Agent 与程序检查分别出具结果；必要时退回修改或待确认。
6. 发送队列显示额度、时段、冷却及预留；未派发不能显示正在发送。
7. 平台建立会话并发送；若存在默认招呼，作为单独消息节点展示。
8. 回读核验具体文本及消息凭据，核验通过才显示“个性化说明已发送”。

企业搜索只在需要且获得原有授权时执行，不让每条简单沟通都触发全套 Agent。协调 Agent 也不必在每次程序读取或每条回复前额外调用模型。

### B. 收到招聘者消息

1. 展示最新真实消息，定位账号、联系人、岗位和消息版本。
2. 程序分类：常规咨询、重要事项、不明确或不适合自动处理。
3. 对适合生成的消息，回复 Agent 使用当前问题、必要会话、已确认事实及相关 JD；资料缺失明确提示。
4. 展示拟回复内容及其依据，进行事实和表达检查。
5. 常规咨询沿用现有自动发送授权；重要事项进入本人确认。
6. 发送前重新核对会话、输入框、草稿、资料及最新消息；变化则旧稿失效。
7. 展示平台核验或“发送结果不确定”，不自动重试。

收到“你在上海吗”时，应直接回答已确认地点，不重复介绍全部工作经历；收到项目能力问题才展开对应经历。不默认附加“方便介绍岗位职责和团队情况吗”。

## 5. “怎么回复”必须看得清

回复详情按此顺序展示：

1. **对方原话**：时间、联系人、关联岗位，支持回到消息上下文。
2. **准备回复**：完整草稿、自动／待确认、尚未发送／已发送及草稿版本。
3. **为什么这样回**：一句任务级解释，例如“对方在确认所在地，直接回答已确认地点”。这是简洁结论，不展示模型内部思维链或原始 reasoning 流。
4. **使用的经历**：引用的事实片段、来源、确认状态、资料版本；与 JD 的关联并排显示。
5. **检查结果**：事实有据、回答当前问题、HR 可读、本人视角、长度适当、无重复追问、无越权承诺。分别标明程序检查、模型审校或本人确认，未检查项显示“未检查”。
6. **下一步**：自动队列／等待条件／本人操作，以及可用处理按钮。

“模型认为通过”不替代来源和程序规则。当前测试用的七维评审尚未全部接入生产，实施时需复用现有校验并补齐结果结构，不能只在界面上勾选七个对号。

发送完成后展示实际发出的文本、时间、账号、会话、消息标识和核验方式；如果它与草稿不同，应单独提示差异并停止自动计成功。手动确认的结果与平台回读分列。

## 6. 如何介入主 Agent 或子任务

建议提供明确范围的“调整本次任务”，可输入“这次只强调企业 AI 落地，不重复介绍 App 数据”等指令。

| 操作 | 生效规则 |
| --- | --- |
| 修改本次回复 | 先以版本校验取编辑权并阻止该稿进入新发送；编辑后重新审校，原确认失效 |
| 补充本次要求 | 只作用于选中任务，保存成版本化输入；若模型调用已发出，不悄悄修改其提示词 |
| 取消并重新生成 | 明示可能产生新调用；旧结果保留但不可用于发送，创建关联的新尝试 |
| 暂停本条流程 | 当前对象后续步骤暂停，其他任务按原策略执行 |
| 跳过／放弃岗位 | 展示停止范围和原因；保留来源与已发送事实 |
| 查看或修改角色提示词 | 跳转 Agent 管理并定位；保存后旧版本任务按现有失效机制终止／失效，不能假装在途调用已更新 |
| 重要事项确认 | 绑定准确账号、会话、最新消息、内容及附件；任一变化后失效 |
| 核实发送结果 | 已发送／未发送／仍不确定；选择未发送不会自动重发，须明确重新入队 |

自然语言建议由程序转换为有限的操作提案，显示作用对象和差异；不能直接执行模型返回的任意接口。全局方向、薪资、额度和发送授权仍从设置中修改。本次偏好不会自动写入简历事实或全局策略。

编辑和发送存在竞态：服务端若已取得发送权，编辑入口应返回“已进入发送／核验，不能更改本次内容”，不能只靠前端关闭按钮。任何真实自动消息依旧使用原有发送队列。

## 7. 状态与进度规范

| 状态 | 界面必须说明 |
| --- | --- |
| 等待执行 | 等待哪项依赖或资源：模型、账号操作、额度、时段、冷却 |
| 正在执行 | 实际步骤、开始时间、已用时间、最近心跳 |
| 待你处理 | 具体缺失事实或待确认内容，以及唯一主要处理入口 |
| 已暂停 | 本条／发送／全部自动任务；由谁暂停；恢复入口 |
| 已失效 | 哪个资料、JD、消息、策略或提示词版本变化 |
| 失败 | 可读原因、保留了什么、重试是否产生模型调用 |
| 核验不确定 | 已尝试发送但凭据不足；禁止自动重发 |
| 已完成／已跳过／已取消 | 具体完成目标或停止原因，不能混为发送成功 |

“阻塞”不统一算作失败；目前 `recordTask` 的 blocked→failed 映射需要修正，新增原因码后保留旧记录原始状态，不反向猜测历史原因。

仅在步骤总数确知时显示“完成 3／5 个已确定步骤”；可动态增加步骤的流程显示当前阶段和事件列表。模型生成仅显示请求已提交、等待输出、输出接收、校验等可观测阶段，不伪造百分比或剩余时间。超过心跳阈值显示“连接／执行状态待核实”，不直接当作失败重跑。

主 Agent 的规划调用完成与整个业务流程完成分开显示。任务树是依赖关系，不意味着所有子 Agent 同时运行；当前模型调用仍遵循串行租约，平台操作遵循账号串行与人工优先。

## 8. 后端设计：给现有执行链补可追踪性

### 统一标识与记录

继续使用 `atlas.db`、现有任务服务和发送队列。新增轻量关联及事件表，不复制业务对象或重建调度器。

- **运行实例** `execution_runs`：rootRunId、账号、触发来源、工作对象、planId/actionId、创建时间、版本依据。一个岗位联系或会话回复是一条业务运行，批次为分组，不让当天所有工作成为一个永不结束的根任务。
- **步骤实例** `execution_steps`：stepId、runId、parentStepId、执行者类型／AgentId、名称、状态、原因码、开始／结束／心跳、attemptId、输入版本及输出引用。
- **依赖与关联** `execution_links`：关联已有 taskId、aiCallId、contactId、sendAttemptId、messageId，以及复用的分析／草稿；支持一条任务多次模型请求和工具回合。
- **步骤事件** `execution_events`：递增序号、幂等事件键、对象、事件类型、时间、受控摘要、引用。只追加历史，当前状态由事务内同步更新的投影读取。
- **介入记录**：操作人、作用范围、输入版本、内容差异、结果和时间；复用现有草稿及确认存储，事件只记录引用。

关联必须在创建或执行时显式传递，不能按时间相近或公司名称猜。直接操作模块创建独立根；协调派发时携带 planId/actionId。历史无关联时标注“历史记录，流程关联未知”。

当前部分表使用 `INSERT ... VALUES` 依赖固定列数，迁移优先新增关联表；如需扩列，必须同步将全部相关写入改为显式列名。

### 实际埋点

任务入队、获得租约、开始模型请求、工具开始／结束、模型返回、格式校验、事实审校、生成草稿、规则拦截、等待确认、领取发送权、点击发送、回读、失败／取消各自写事件。心跳更新不逐秒追加历史。

显示每个工具的名称、用途、脱敏参数摘要、结果数、公开来源及耗时，不保存搜索页全部 HTML、密钥或整份简历到日志。对网页未支持的工具能力明确显示不可用。

引用简历、JD、会话和提示词的版本与摘要，尽量复用已有内容；草稿保存在业务记录中。已保存的来源发生删除时标注不可用，不用当前内容冒充历史快照。删除和备份遵循现有个人数据管理规则；导出诊断默认脱敏。

### 事务与故障语义

本地状态更新和关键事件在同一事务写入；外部模型／平台操作与 SQLite 不能原子提交，因此先保存意图、后执行、再记录凭据。启动恢复先核对检查点和外部结果，绝不根据“没有完成事件”重新发送或自动重复付费请求。

事件记录是观测层：不能绕过现有幂等键、账号租约、预算或发送确认。关键审计记录无法落库时停止新发送；界面订阅断开则不影响服务端任务，显示最后同步时间。

### 共用查询与交互接口

- `career-execution-list`：按账号、状态、对象分页查询。
- `career-execution-detail`：运行树、当前步骤、产出引用和可用动作。
- `career-execution-events`：按 sequence/cursor 增量读取，带缺口标识。
- `career-execution-control`：操作、作用范围、baseRevision、idempotencyKey；转交现有执行器。

桌面 IPC 与本机 HTTP 共用处理器。首版采用增量查询：前台有活跃任务每 2 秒，无活跃任务降频；隐藏页面停止非必要轮询，恢复后先补快照再读增量。后续如需推送，再增加 SSE／IPC 订阅，保留同一事件协议。多个页面共用订阅管理，禁止每个节点独立轮询。

跨账号鉴权每次检查；切换账号取消旧订阅并清空旧对象视图。查询限页、索引按账号／状态／更新时间和运行／序号建立，长历史折叠。运行事件默认保留 90 天；发送、确认、版本凭据随业务历史保留，清理后应明确显示“详细运行日志已过保留期”。

## 9. 实施顺序与验收

| 阶段 | 交付 | 验收门槛 |
| --- | --- | --- |
| P0 运行链路 | 关联 ID、步骤状态、关键事件、共用查询 | 一个自动联系和一个常规回复能完整关联任务、模型、草稿、发送凭据；独立触发来源正确；历史不补造 |
| P1 界面可见 | 总览摘要、任务树、结果详情、Agent 配置跳转 | 从总览三次点击内看到当前对象、实际 Agent、当前步骤、阻塞原因和下一步；不混淆启用与运行 |
| P2 回复与介入 | 证据卡、审校结果、草稿编辑、局部暂停、重要事项确认 | 常规自动发送、重要事项人工确认均沿用授权；草稿变化／新消息使旧确认失效；不追加通用追问 |
| P3 稳定交付 | 恢复、分页、跨页联动、真实读取、说明 | 双窗口、重启、取消、暂停竞态、账号切换、网络中断均不重复付费／发送；读不到结果时明确待核实 |

优先完成 P0＋P1：先让你看见真实运行和结果，再增加细粒度的人工调整。首版不引入自由派生 Agent、每个 Agent 独立聊天窗口、模型内部思维直播或复杂拖拽编排器。

### 必测场景

1. 主 Agent 安排后调用已结束，子任务继续：两者状态准确区分。
2. 手动生成回复：显示由本人触发，不伪造主 Agent 调度。
3. 一个招呼经生成与独立审校：两个真实调用关联同一任务；缓存不重复计用量。
4. 岗位不匹配：展示停止原因；无招呼、无发送。
5. 同一会话的地点、项目、薪资、简历、面试咨询：分别检查短答、经历引用和人工确认路径。
6. 模型调用工具：可看到实际工具开始／结果／失败与引用来源；无需泄露敏感输入。
7. 默认招呼成功而个性化说明未发：只显示已开聊，不计完整联系成功。
8. 生成后用户输入、新消息、资料／模型／提示词版本变化：阻止旧稿发送。
9. 编辑与发送同时发生：由服务端确认哪一方取得操作权，无“界面改了但发了旧稿”的误导。
10. 点击发送后断网／进程退出：显示不确定，不自动重发；人工核实有记录。
11. 两个窗口同时取消、恢复、确认：幂等且版本冲突可见。
12. 心跳丢失、账号切换、隐藏页面、事件缺口：有明确状态并能恢复，不整页刷新 BOSS。
13. 5,000 条运行、50,000 条步骤事件的隔离数据：常用分页 P95≤1 秒，初始列表≤20 条，不加载全量结果；连续切页不增加残留轮询。
14. 1280×720、1920×1080、窄窗口及键盘操作：内容不截断，状态不只靠颜色，详情单层滚动。

保留现有回归测试并加入以上必要场景。离线样例和模拟平台覆盖竞态；真实账号只验证必要读取与确实准备发送的合适内容，不能发测试消息充数。真实能力未验收的部分保持“待验收”。

## 10. 用户最终看到的结果

例如：“某企业／AI 产品负责人：岗位分析完成 → 已生成招呼 → 正在审校；拟发送内容可查看，引用 2 条已确认经历。下一步为进入发送队列。”

对常规回复：“对方问所在地 → 已生成一句直接回答 → 检查通过 → 等待冷却；可暂停本条或编辑。”

对重要事项：“对方索要简历 → 等你选择附件并确认；尚未发送。”

这三种状态必须从任何相关页面看到同一份记录，并能定位到同一任务和同一结果。
